2026-05-07 Nether/Codex multiplayer coordination requirement

Requirement: one Sheltered session identity source

DRY rule
- Sheltered multiplayer gameplay systems must read the active SessionId, local gameplay player id, and session roster from one shared Sheltered-owned session context.
- Gameplay integrations must not independently read SessionId from multiple places such as NetworkSession.SessionId, setup payload DTOs, save metadata files, and hook session state.
- If a gameplay system needs session identity, it should consume the shared Sheltered multiplayer session context or a narrow adapter around it.

Why this is required
- The session id already owns the multiplayer master seed pipeline.
- Player id assignment, bunker placement, save setup, world-start gating, and later gameplay sync must agree on exactly the same session identity.
- Multiple direct reads force future maintainers to remember hidden coupling between systems, which violates DRY and separation of concerns.
- Duplicated reads make later changes dangerous: a reconnect flow, setup payload migration, host migration path, or save-resume path can update one source while another feature keeps reading stale or differently normalized session data.

Boundary rule
- ModAPI.Networking remains the neutral transport/session layer and may expose NetworkSession.SessionId as protocol/session metadata.
- ShelteredAPI owns the gameplay meaning of that id.
- Sheltered gameplay code should not treat NetworkSession as the gameplay session context. It should cross into the networking layer through one integration point, then pass a Sheltered-owned context to seed, bunker, save, and startup systems.

Required shape for future refactor
- Add or use a single Sheltered multiplayer session context that exposes:
  - SessionId
  - Local gameplay player id
  - Network local peer id when needed for transport mapping
  - Host/client mode
  - Current deterministic player roster
- The session seed application and bunker assignment code must both read SessionId through that same context.
- Setup payloads may carry serialized session data over the wire, but after deserialization they must populate/update the shared context rather than becoming a second long-lived source of truth.

Implemented coordinator lifecycle
- ShelteredMultiplayerSessionCoordinator is the Sheltered-owned startup/session source of truth.
- It owns:
  - SessionId
  - local gameplay player id
  - network local peer id
  - local stable peer id
  - host/client mode
  - connected peer roster
  - bunker assignment records
  - setup settings
  - setup phase/state
- Startup phases are raised synchronously and in registration order:
  - SessionActivated
  - RosterChanged
  - SetupPreparing
  - SetupReceived
  - LocalWorldLoaded
  - WorldStartReleased
  - SessionDeactivated
- Startup-critical handlers must be registered as critical. The coordinator logs and rethrows critical handler failures so setup does not continue with partially applied seed, setup, bunker, or world-gate state.

Implemented ownership split
- ShelteredMultiplayerSetupService is the transport/setup-message orchestrator. It may serialize and deserialize setup wire records, but it must immediately publish received setup data into ShelteredMultiplayerSessionCoordinator.
- SetupService must not call ShelteredBunkers, apply session seeds, or apply gameplay difficulty directly.
- ShelteredMultiplayerBunkerAssignments is a coordinator lifecycle handler:
  - Host assignment runs from SetupPreparing/RosterChanged using context SessionId plus stable peer identity.
  - Host remains gameplay player 1.
  - Connected clients sort deterministically and receive gameplay player IDs 2, 3, etc.
  - Host-provided bunker roster is serialized only as setup wire data, then restored into coordinator state on the client.
  - Both host and client application paths load definitions through ShelteredBunkers from coordinator state.
- ShelteredMultiplayerSessionSeedApplicator is a coordinator lifecycle handler. It applies ModRandom seed from context SessionId, not from setup DTOs or NetworkSession.
- ShelteredMultiplayerHookService projects coordinator state into the public hook SessionState and owns world-start block/release effects from coordinator phases.

Review checklist
- Search for direct gameplay reads of NetworkSession.SessionId.
- Search for setup DTO SessionId being passed directly into gameplay services.
- Confirm all Sheltered gameplay systems use the shared context before deriving seeds, player ids, bunker positions, or save metadata.
- If a new feature needs session identity, add the data to the shared context instead of adding another direct dependency.
